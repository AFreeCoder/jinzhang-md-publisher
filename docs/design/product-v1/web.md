# 锦章一期设计：网页版（门户 + 在线排版）

状态：已评审，2026-09-10 定稿（issue #5）；已实现，2026-09-18 起在 https://jinzhang.ink 上线（部署见 [deployment.md](../../deployment.md)），2026-09-30 按线上版本 `4d312c0` 同步本文。2026-09-08 起草，2026-09-09 按用户决定改为 Next.js，同日合并 Codex 评审。上游：[需求文档](../../requirements/product-v1/requirements.md) 功能 2、17、25、29 与业务规则 6.1、6.2、6.3、7.3；过程记录在 [issue #5](https://github.com/AFreeCoder/jinzhang-md-publisher/issues/5)（网页版）、[issue #9](https://github.com/AFreeCoder/jinzhang-md-publisher/issues/9)（上线后的排版页优化）、[issue #14](https://github.com/AFreeCoder/jinzhang-md-publisher/issues/14)（中转保留期改为 1 天）与 [issue #4](https://github.com/AFreeCoder/jinzhang-md-publisher/issues/4)（总体架构）。总体架构与 core 见 [architecture.md](architecture.md)，本文只写网页版这个壳，不另写一套转换规则。

## 1. 结论

- 网页版是一个 Next.js 应用（App Router，服务端模式）：门户首页加在线排版页，没有账号、数据库和文章上传。排版、预览、复制全部在浏览器里由 core 完成；服务端只有图片中转的两个接口（签发上传条件、校验已上传对象并发放限时读取地址），另有一个供容器健康检查与发布核对用的 `/api/health`
- 复制路径按平台分两条：复制到公众号时图片以 data URL 内嵌进剪贴板 HTML，这是 my-toolbox 日常使用验证过的做法；复制到知乎时剪贴板里放私有 OSS 桶的 24 小时预签名地址，知乎编辑器粘贴时把图片转存到自己的图床（作者用 my-toolbox 多次实际使用证实，2026-09-10 本项目真实草稿复验通过）。图片在插入编辑区时就在后台上传，知乎复制直接复用
- 预览放在带 `sandbox` 的 `iframe` 里渲染，与页面样式隔离、不执行脚本；预览与复制使用同一份 core 输出
- 页面视觉：纯白底、墨色文字、朱砂强调色，品牌标识是红底白字的「锦章」双字印章；首版视觉提案在 `prototypes/web-v1`，结构与细节以线上实现为准
- 选 Next.js 而不是纯静态构建的理由：中转接口必须在服务端做，密钥不能进前端；网页版后续的服务端能力在同一代码库里加，不用迁移。代价是需要 Node 运行时来部署

## 2. 页面与路由

| 路径 | 文件 | 内容 |
|---|---|---|
| `/` | `app/page.tsx` | 门户首页，服务端渲染的静态页，见 2.1 |
| `/format` | `app/format/page.tsx`、`app/format/workspace.tsx` | 在线排版页，见 2.2 |
| `/api/transit/sign` | `app/api/transit/sign/route.ts` | 签发单个对象的上传条件，见 4.3 |
| `/api/transit/complete` | `app/api/transit/complete/route.ts` | 校验已上传对象，发放限时读取地址，见 4.3 |
| `/api/health` | `app/api/health/route.ts` | 返回运行版本（`APP_REVISION`）与中转配置是否齐备；齐备 200，缺项 503。只用于容器健康检查与发布核对，不代替 OSS 连通性验收 |

浏览器边界：排版页组件在客户端组件 `app/format/page.tsx` 里用 `dynamic(() => import('./workspace'), { ssr: false })` 加载；IndexedDB、`localStorage`、剪贴板 API 只在工作区组件的生命周期与事件处理里访问。core 的浏览器构建与高亮语言只在 `/format` 加载，门户不下载它们。

### 2.1 门户首页

- 顶栏：品牌印章、「排版样式」锚点、GitHub、「开始排版」；窄屏保留 GitHub 与「开始排版」
- 首屏：标语「让文字，锦绣成章。」、一句说明、三个标签（原生 Markdown、本地处理正文、无需注册），右侧是原文到成品的示意图
- 三张入口卡片：在浏览器里排版（跳 `/format`）；让 Agent 帮你发布（skill）；留在 Obsidian 里（插件）。后两张的安装命令与仓库地址在构建时由环境变量 `JINZHANG_SKILL_INSTALL`、`JINZHANG_OBSIDIAN_REPO` 注入，未配置时如实显示「即将提供」，不虚构入口
- 「文字有风格，排版也有」一节用文字卡片介绍三套公众号主题，不放截图
- 页脚显示版本号，取自 `apps/web/package.json`

### 2.2 在线排版页

布局：桌面三栏，左原文、中成品预览、右排版设置（设置栏 260px，1500px 以上 285px）。1100px 以下设置收进抽屉，由顶栏的「排版设置」打开，Esc 或点外部关闭。720px 以下改为单栏，用「编辑 / 预览」切换，同一时刻只展示一个工作区。工作区占满视口剩余高度，编辑、预览、设置各自滚动，页面本身不滚动。文章 HTML 不使用页面壳的样式。

- 顶栏：桌面合并为 60px 单行，窄屏两行共 108px。左侧品牌与「在线排版」，中间平台分段控件（微信公众号、知乎）与复制主按钮相邻，右侧「更多操作」菜单：新建文章、恢复上一稿（有上一稿时出现）、载入示例、清除本地数据、GitHub。菜单支持点外部与 Esc 关闭，并把焦点还给入口
- 原文栏：「Markdown 原文」标签旁是「＋ 插入图片」；其下是标题输入框与「用正文一级标题」按钮，提示「标题仅用于预览」（第 8 节）；编辑区统一 16px 等宽字体；编辑区下方依次是补图面板、上传失败重试、原文警告，底栏显示上传进度与字数
- 预览栏：「成品预览」标签旁是「自适应 / 手机」宽度切换（第 6 节）
- 设置栏：「排版主题」三选一，只在公众号下可选，知乎下显示「知乎使用平台原生阅读样式」；「文章开头与结尾」见第 7 节
- 底栏：本地保存状态（已恢复、已保存、保存失败）
- 新建、载入示例与恢复上一稿：替换当前文章前确认，并在本浏览器保留一份上一稿；只替换原文和标题，平台、主题及两个平台的固定内容设置保持不变。清除本地数据同时删除上一稿

原文警告：core 在 `prepare` 阶段产生的 `FRONTMATTER_IGNORED`、`UNSUPPORTED_SYNTAX`、`HTML_STRIPPED`、`TITLE_TOO_LONG` 在编辑区底部常驻一行，随最新排版结果更新；`IMAGE_MISSING` 由补图面板承担。

### 2.3 本地存储与示例稿

| 位置 | 内容 |
|---|---|
| `localStorage` `jinzhang.document.v1` | 原文、标题、主题、当前平台、两个平台各自的固定内容设置 |
| `localStorage` `jinzhang.previous-article.v1` | 上一稿（原文与标题） |
| `localStorage` `jinzhang.transit-cache.v2` | 知乎中转地址缓存，见 4.2 |
| IndexedDB `jinzhang-assets` | 图片：`refs`（引用 → 内容哈希）与 `blobs`（内容哈希 → 图片），见 4.1 |

- 首次打开（本浏览器没有保存过文档）与清除本地数据之后，编辑区是示例稿：一份常用 Markdown 语法速览，标题「把写作还给写作」，配图 `/sample-cover.jpg` 按当前站点地址拼接，本地与线上都能显示。新建文章是空白
- 示例升级：恢复文档时，若正文与历代内置示例之一逐字相同且标题仍是示例标题，换成当前示例，平台与排版设置保留；改过的稿子不动。历代示例原文存于 `apps/web/lib/legacy-samples.ts`，更换示例文案时必须把上一版追加进去，否则存过旧示例的浏览器会一直停在旧稿
- 示例里不放两个相邻的代码块（知乎会在中间插空段防止合并，预览里显得空一大块），分隔线不紧贴标题
- 本地数据损坏或存储不可用时不覆盖原数据，提示用户先保留原文

## 3. 数据流

```
Markdown 文本 + 已插入的本地图片(IndexedDB) + 页面配置(主题/平台/固定内容/标题)
      │
      ▼  core.prepare({ markdown, title, templates },
      │               { platform, fixed, resolver: BrowserAssetResolver, config: { date, author } })   异步
PreparedArticle { tree, images[], cover, warnings[], version }
      │
      ▼  core.render(prepared, { theme })                                                          同步纯函数
RenderResult { html, text, images[], warnings[], degraded[], stats, version }
      │
      ├─▶ 预览：再跑一次 render(prepared, { theme, sourceLocations: true })，图片换成 blob: 地址，
      │         previewDocument(result, html, { hideCover: true, date }) → iframe srcdoc
      │
      └─▶ 复制：placeImages(result, CopyImageStore(platform)) → ClipboardItem { 'text/html', 'text/plain' }
              公众号：图片规范化后内嵌为 data URL
              知乎：  复用插图时已取得的中转地址，缺失或过期的在这里补传（4.2）
```

- 每次输入、平台或固定内容变化都产生新的 `version`；`prepare` 与 `render` 的结果带着它回来，晚返回的旧版本直接丢弃，不覆盖新稿。`prepare` 结果按输入、平台、固定内容与模板变量缓存，切换主题只重跑 `render`
- 输入变化后 300ms 防抖再排版；主题、平台切换立即执行
- 编辑期间保留上一帧结果：字数、缺图面板、复制按钮都不随按键闪动。复制点击落在防抖或排版进行中时，剪贴板写入仍在点击的同步调用链里发起，载荷先等待当前版本的排版结果再组装；版本再变化则旧等待作废，不会复制旧正文
- 一期在主线程执行。这不是性能结论，只是系列文章体量下的起点（2026-09-11 实测 200 节、1.4 万字的长文 `prepare` 加 `render` 约 130ms）；出现可感知卡顿时把 `prepare` 与 `render` 移进 Web Worker，接口不变

## 4. 图片

### 4.1 本地图片进入文章

需求 17 与业务规则 6.2 要求：粘贴图片或选择本地文件能插入文章；只贴入了 Markdown 但本地路径无法读取时，指出缺失并提示补充。

- 入口：在编辑区粘贴图片、把文件拖进页面任意位置、或点「插入图片」选择文件。拖进编辑区时插在鼠标落点，拖到预览区或页面其他位置时插在当前光标处；页面整体拦截文件拖放，不会离开页面
- 图片先用 core 的 `CanvasImageCodec` 探测能否解码（原文件 12MB、4000 万像素以内），再存入 IndexedDB，并在插入点写入 `![文件名](jz-local://<assetId>)`。这个地址只在网页版内部有意义
- 插入用浏览器原生的 `insertText`，保留撤销与重做历史，光标落在图片之后；图片处理期间可以继续打字，插入点跟随前文编辑移动，不覆盖后来输入的内容
- 两张映射表：`refs`（原始引用 → 内容哈希）决定文章里哪一处引用对应哪张图，`blobs`（内容哈希 → 图片）只做去重。补图绑定的是某一处具体的缺失引用，同名文件在不同目录也不会被自动当作同一张（Codex 评审 W4）；写入 IndexedDB 成功后，才用 core 的 `replaceImageReference` 把 Markdown 里这一处引用精确改写为 `jz-local://`，支持中文与空格路径、引用式定义和原始 HTML 的 `<img>`
- `BrowserAssetResolver` 把 `jz-local://` 与已绑定的原始引用解析为 `blob` 类资源；相对路径、绝对路径在浏览器里读不到文件，解析结果为「缺失」；`http(s)` 地址为 `remote`；`data:image/...` 直接解码
- 缺失图片在预览里显示为「图片缺失：<引用>」占位块；编辑区底部按引用显示「补图」按钮，直接选择对应文件，不弹二次确认窗口
- 后台上传：插入或补图后立即在后台规范化并上传中转桶，不论当前选的是哪个平台，供知乎复制复用。上传状态只统计当前正文仍引用的图片，删掉的图片不再显示；失败保留本地图片并在编辑区提供「重试上传」，正文编辑不受影响
- 「清除本地数据」删除 IndexedDB、`localStorage` 里的全部内容与中转缓存，回到首次打开的示例稿

IndexedDB 只存当前浏览器；刷新页面后原文从 `localStorage` 恢复、图片从 IndexedDB 恢复，两者按引用对上。原图始终保留在本浏览器。

### 4.2 复制时图片怎么落地

core 定义 `ImageStore` 接口：`put(image, ctx)` 收到一张图片的引用与已解析的来源，返回放进 HTML 的 `src` 与目标交付方式需要的附加属性。网页版只有一个实现 `CopyImageStore(platform)`（`apps/web/lib/clipboard.ts`），用 core 的 `CanvasImageCodec` 按 `NORMALIZE_PROFILES.clipboard`（长边 1600px、单张 1MB，透明图保留 PNG，其余转 JPEG）规范化，网页版不另写规则：

| 平台 | 行为 | 依据 |
|---|---|---|
| 公众号 | 规范化后编码为 `data:image/...;base64,...` 写进 `src`，不经过中转桶，也不等待后台上传 | my-toolbox 的公众号复制就是这条路，作者日常使用验证过粘贴后图片保留 |
| 知乎 | 按规范化后内容的 SHA-256 查中转缓存，命中则复用地址；未命中经 4.3 的两个接口上传，取得预签名地址。缓存同时存内存与 `localStorage`，条目保留 20 小时（比 24 小时的读取地址提前 4 小时失效），过期后从本地原图重新上传；旧键 `jinzhang-transit-cache` 里按 6 天写入的条目不再读取，访问缓存时删除。当前正文引用的图片上传完成前，知乎复制按钮不可用 | my-toolbox 的知乎路径就是先把图片换成公网地址再复制；2026-09-10 真实知乎草稿里中转图片全部转存到知乎图床 |

- 远程图片：公众号路径先在浏览器里读取（不带凭证与来源页，12MB 以内）转成 data URL，跨域读不到时保留原地址；知乎路径直接保留原地址，由知乎编辑器抓取。两种保留都给 `IMAGE_REMOTE_KEPT` 提示「粘贴后请在平台里核对」
- 动图取首帧并提示；SVG 先检查不含脚本与外部资源，再栅格化，失败则指出是哪一张
- 同一次复制里内容相同的图片只处理一次
- 界面不显示内嵌、上传的数量与临时存储期限：2026-09-10 用户走查裁定删除这类常驻说明，过期由程序自动重传承担（与需求文档的差异见第 13 节）

### 4.3 中转桶与两个接口

- 桶：阿里云 OSS 专用私有桶（生产为北京地域的 `jinzhang-md`），私有读写、禁止匿名列表、关闭版本控制；`transit/` 前缀设 1 天生命周期删除（OSS 每天北京时间 8 点执行，对象在上传后 1 到 3 天之间删除，不早于 24 小时）；CORS 只放行本站 Origin 的 POST 与 GET（生产 `https://jinzhang.ink`，另保留本地开发 Origin）。应用凭证只授予 `transit/` 前缀的读、写、删。未通过校验的对象不会成为可访问图片
- 对象键：`transit/<YYYYMMDD>/<随机 UUID>.<png|jpg>`
- `POST /api/transit/sign`：请求 `{ mime, size }`，只接受 `image/jpeg`、`image/png`，大小 1 字节到 10MB。返回 `{ url, fields, ticket, expiresAt }`：`fields` 是 OSS 表单直传（PostObject）的 V4 签名字段，策略绑定桶、对象键、`Content-Type`、`x-oss-forbid-overwrite: true`、`success_action_status: 201` 与精确的 `content-length-range [size, size]`，5 分钟过期；`ticket` 是服务端签名的票据（对象键、大小、类型与过期时间，HMAC-SHA256），供 `complete` 核对。浏览器拿 `fields` 直传 OSS，服务端不经手图片字节
- `POST /api/transit/complete`：请求 `{ ticket }`。核对票据签名与过期；HEAD 对象，大小或类型与票据不符则删除并拒绝；再下载对象，校验魔数是 JPEG 或 PNG、像素不超过 4000 万、sharp 能完整解码，不通过则删除并拒绝。全部通过返回 24 小时有效的 V4 预签名 GET 地址（ali-oss `signatureUrlV4`，签名只对 GET 有效）。网络故障不当作文件损坏，不删除对象
- 两个接口共用的约束：请求头 `Origin` 必须等于 `JINZHANG_ORIGIN`，否则 403；只收 JSON，请求体不超过 4KB；中转未配置返回 503 `TRANSIT_NOT_CONFIGURED`；其他异常返回 502 `TRANSIT_UNAVAILABLE`；响应不缓存。OSS 密钥与票据密钥只在服务端环境变量里
- 限流与容量在网关做，不写业务代码（生产配置见 [deployment.md](../../deployment.md)）：两个接口按 IP 共用每分钟 60 次、滚动 24 小时 1000 次上限，超出返回 429；`complete` 后端最多同时完整解码两张图，排队上限 8、最多等 5 秒；入口请求体上限 8KB。计数在网关内存里，重启清零，不用于计费
- 说明文案分开写两件事：链接 24 小时后失效；桶内对象按生命周期规则清理，清理任务按周期执行，不承诺到期那一刻所有副本已删除
- 代码结构：`lib/transit/service.ts` 是与 Next.js 无关的标准 `(Request) => Promise<Response>` 处理器与 `ObjectStore` 接口，`lib/transit/oss.ts` 是 ali-oss 适配，路由文件只做挂载

## 5. 剪贴板

- 用 `navigator.clipboard.write([new ClipboardItem({ 'text/html': htmlPromise, 'text/plain': textPromise })])`。写入调用发生在用户点击的同步调用链里，ClipboardItem 的值传 Promise，图片处理与上传在 Promise 内完成，这是 Safari 与 Chrome 都支持的异步写法。两个 MIME 共用同一个准备任务，不重复上传
- `text/html` 是 core 的平台成品 HTML，不含标题与封面；`text/plain` 是成品的可见文本（不是 Markdown 原文，纯文本粘贴是降级，不冒充「导入 Markdown」）
- 复制主按钮宽度固定（桌面 124px），文案随状态变化：「复制到公众号 / 知乎」「正在复制…」「已复制 ✓」（2.5 秒后恢复）。正文有缺图时点复制，按钮显示「请先补齐图片」并聚焦首个补图按钮，不复制
- 复制过程中改稿、切平台、换图片或改固定内容，旧任务作废；图片上传独立于文章编辑，本地副本保留
- 失败时在页面底部浮出一条提示（不挤动工作区），写明具体原因（浏览器不支持富文本剪贴板、未允许写入剪贴板、剪贴板写入超时、图片准备失败），附「重试复制」；正文已准备好、只是写入失败时，另有「手动复制」。重试复用已上传的图片。超时：图片准备 60 秒，剪贴板写入 20 秒
- 「手动复制」即全选预览区复制：预览换成只含正文的版本（不含标题栏、封面与诊断，去掉原文行号属性）并全选，提示按 ⌘C / Ctrl+C，浏览器原生的选区复制会带上富文本与图片；纯文本复制不算格式与图片完整。不再弹 HTML 源码文本框（Codex 评审 W1）
- 复制成功后若有图片提示（远程图片保留原地址、动图取首帧），以轻提示显示

## 6. 预览

- `iframe` 加 `sandbox="allow-same-origin"`（`blob:` 图片需要同源；不允许脚本、表单与顶层导航），`srcdoc` 由 core 的 `previewDocument` 生成，页内另有 CSP：`default-src 'none'`，图片只允许 `blob:`、`data:` 与 `http(s)`，样式只允许内联
- 预览壳：顶部标题区（标题，留空时显示「未命名文章」；「账号名（预览示意）」与当天日期），其下是正文。网页版只复制正文，调用时传 `hideCover: true`，不显示封面区；其他客户端保持封面区
- 名片等只有平台才渲染的组件在预览里用占位块表示，由预览壳的样式画出（名称与简介），不进成品；网页版固定内容不含名片，目前不会出现
- 知乎预览壳套一份精简的知乎阅读样式（标题字号、正文 15px 行高 1.7、引用左边线、代码块底色、表格边框），正文用 core 的知乎结构输出；core 返回的 `degraded` 列表（h4 及更深标题降级、装饰样式移除、名片移除）附在预览末尾逐条标出
- 预览里的本地图片用 `URL.createObjectURL(blob)`，旧地址在新预览生效后释放。预览与复制的差别只在图片的 `src` 与附加属性，以及预览多出的原文行号属性，其余 HTML 相同
- 宽度：默认「自适应」，画布跟随预览栏，最宽 860px；「手机」模式画布 420px，预览栏同步收至 444px，剩余宽度交还原文栏，画布外用浅灰底、28px 圆角与淡阴影区分设备外部；预览壳在 480px 以内左右内边距 16px。720px 以下隐藏宽度切换
- 动效：宽度切换用 Web Animations 在实测像素值之间过渡栏宽与画布宽（340ms），中途可以折返；分段控件的滑块、按压反馈、弹窗与抽屉、菜单与提示都有进出过渡。系统设置减少动态效果时直接到位
- 同步定位：原文和预览按原文行号双向同步滚动，点击预览正文把原文光标定位到对应行；点击链接、选择文字不抢焦点。行号来自 `render(…, { sourceLocations: true })` 输出的 `data-source-line`，只用于预览，自动复制与手动复制均不携带
- 把图片文件拖进预览区，同样插到原文当前光标处
- 编辑区底栏显示可见字数。接口 HTML 预算、剪贴板体积、清理日志等开发诊断信息不显示；复制路径不受公众号草稿 API 的 20000 字符上限约束，`CONTENT_NEAR_LIMIT` 不展示

## 7. 固定内容

- 网页版只提供纯样式的开头结尾（需求 29），不含名片等需要账号资料的元素。两个平台分别保存，默认都关闭
- 开头：开关打开后展开样式与字段。样式「简约署名」或「留白分隔」（后者在前面加一条分隔线）；字段：作者名、口号
- 结尾：样式「一句寄语」或「细线落款」（后者在前面加一条分隔线）；字段：结尾话术（默认「愿每一次认真表达，都被好好看见。」）、合集链接。合集链接生成一行「继续阅读」链接，承担需求 15「往期文章」入口；缺协议时自动补 `https://`，无效或非网页协议的地址在失焦时就地提示
- 关闭开关收起字段，但保留已填内容
- 表单文字按字面输出：Markdown 标点被转义，不做 `{{title}}` 这类变量替换（与需求文档的差异见第 13 节）。表单内容组装成开头、结尾两段 Markdown 交给 core，core 分别包进 `section.jz-header`、`section.jz-footer`，由主题统一着色
- 本地形态的模板文件、变量与 `:::card` 名片见 architecture.md 第 6 节，网页版不走那一套

## 8. 标题

网页版没有文件名，标题只用于预览壳：原文栏顶部的标题输入框留空时，按业务规则视为缺省，预览壳显示「未命名文章」。输入框旁提供「用正文一级标题」按钮，由用户主动点选，不静默把 H1 当标题（Codex 评审 W3）；提取用 core 的 `extractMarkdownTitle`，只取正文顶层一级标题的可见文本，忽略代码、引用与 frontmatter，支持 Setext 写法。标题与正文首个一级标题相同时，预览与复制都不重复输出这个 H1；标题留空时 H1 留在正文里随复制。复制内容不含标题，标题在平台编辑器里填写。

## 9. 工程

- 目录 `apps/web/`：Next.js 16（App Router）、React 19、TypeScript；Tailwind CSS 4 只作基础层，页面样式写在 `app/globals.css`；没有引入 shadcn/ui 等组件库
- `next.config.ts`：`output: 'standalone'`；`transpilePackages: ['@jinzhang/core']`；`ali-oss`、`sharp` 作为服务端外部包
- 依赖 `@jinzhang/core` 的 `.`、`./preview`、`./browser` 三个入口。`pnpm check` 里的 `scripts/check-browser-boundary.mjs` 把 core 产物与 `lib/clipboard.ts` 按浏览器打包，拒绝 Node 内置模块、sharp、ali-oss 与投递代码，并扫描 Next 客户端产物里没有服务端密钥的变量名
- 测试：Vitest，截至 `4d312c0` 共 45 项（core 的渲染、评审回归与浏览器资源，网页版的文档恢复、编辑、剪贴板与中转服务）；Playwright 端到端 25 项（`apps/web/e2e/workspace.spec.ts`，覆盖插图与上传、补图恢复、两平台真实剪贴板载荷、失败重试、快速改稿、手动复制、新建与上一稿、长文同步、窄屏、示例升级与过渡动效）。CI 的 Check 工作流在每次推送与 PR 上跑 `pnpm check` 与端到端；本地用 `PLAYWRIGHT_CHANNEL=chrome` 走已装的 Chrome。端到端里的 OSS 返回是隔离模拟，不代表真实云端验收
- 部署：Docker 镜像（Next standalone）由 Container image 工作流在 main 推送时构建到 GHCR，按 digest 部署到 silicon，前面是 HAProxy 网关与宿主 Caddy（HTTPS）；域名 `jinzhang.ink`，DNS 托管在 Cloudflare。发布、验收与回退见 [deployment.md](../../deployment.md)
